# API conventions

How the FastAPI app in `apps/api` behaves at its edges.

## Errors are RFC 9457 problem details

Every error response has the media type `application/problem+json` and the fields `type`, `title`, `status` and `code`, plus `detail` when it helps and `errors` for 422. `type` is `https://parfocal.eu/problems/{code}`. Raise `BadRequestError`, `UnauthenticatedError`, `ForbiddenError`, `NotFoundError` or `ConflictError` from `parfocal_api.problems` rather than `HTTPException`, and pass a `detail` only when it is safe to show the user. Unknown routes become `not-found`. Any other exception becomes a 500 `internal` problem with a fixed title, and the exception goes to the error reporter. The OpenAPI schema documents the problem responses on every operation, so the generated client knows them. On the client, `toApiError` in `@parfocal/api-client` turns a response into an `ApiError` with a `kind`. Source: FOUND-012 log entry.

## Validation errors never echo input

FastAPI's default 422 body repeats the submitted value in `input`, which could be a patient name. The problem handler keeps only each field's location, message and code. A contract test submits a patient name in an invalid body and checks that it is absent from the response.

## The client is generated, never edited

`pnpm api:generate` writes `packages/api-client/openapi.json` from `create_app` with placeholder settings, then Orval writes `packages/api-client/src/generated/api.ts` and Biome tidies it ([ADR 0017](../adr/0017-orval-api-client.md)). Run it after changing any route or model and commit both files. `test_openapi_contract.py` fails when the served schema differs from the committed file, and the `test` CI job regenerates and fails on any change. Every route needs an explicit `operation_id`, because the generated function names come from it.

Generated calls go through `apiFetch` in `src/fetcher.ts`, which sends the session cookie, returns `{ data, status, headers }` for success and throws an `ApiError` otherwise. Orval only writes `.ts` in its import of the fetcher when its own `tsconfig` option allows `.ts` imports, which `orval.config.ts` sets inline because the package's `tsconfig.json` is solution-style with no compiler options. `openapi.json` is excluded from Biome, which would otherwise reformat it and break the byte-for-byte contract test.

## Who is calling

`authenticate` in `parfocal_api.auth` reads the session cookie and returns a `SignedInUser` or a `PlatformOperator` from `parfocal_api.principals`. `MemberPrincipal` arrives with IAM-005, and `ServicePrincipal` comes from an API token. The guest principal was removed by ADAPT-001 ([ADR 0060](../adr/0060-no-sign-out-permissions-or-guest-scope.md)). Tests that are not about login replace it through `app.dependency_overrides`, which `ApiAs` in `apps/api/tests/db_support.py` wraps so a test calls `api(principal).get(...)`. Never add a header or query switch to pick a principal in application code. See [auth.md](auth.md).

## Every route declares a permission or why it is open

Guard a tenant route with `**require(Permission.X)` from `parfocal_api.permissions`. It refuses roles whose matrix cell is empty and puts `x-permission` into the OpenAPI schema. A route that every member, every signed-in person or nobody signed in may call goes into `OPEN_OPERATIONS` in `apps/api/tests/test_permissions.py` with its reason, and a guarded one needs a request in `GUARDED_CALLS`. The tests fail until one of the two is done. After changing the matrix run `pnpm permissions:doc`. A route that changes something passes `write=True`, which refuses view-only grants, and `test_permissions.py` treats every guarded call that is not a GET as a write. Service accounts reach routes with `Authorization: Bearer pf_...` and only through the permissions in their scopes, so a route that must stay with people checks the principal type, as `/api/me` does ([ADR 0029](../adr/0029-service-accounts-with-own-api-tokens.md)). A route that must allow fewer roles than its matrix cell needs its own check and a test for it. The tenant isolation suite marks each GET route in `GET_ROUTES` that needs admin rights. See [ADR 0096](../adr/0096-researcher-and-reviewer-with-admin-rights.md) (researcher and reviewer with admin rights).

## Admin rights are a flag, not a role

`Role` is only `researcher` or `reviewer`. `memberships.admin_rights` and `invitations.admin_rights` mark a researcher who sets up the workspace, and a check constraint refuses the flag on any other role. `MemberPrincipal.admin_rights` comes from the membership in `auth.resolve`, and `permissions.grant_for(role, permission, admin_rights=...)` gives `Grant.ALL` for the permissions in `ADMIN_RIGHTS` (`manage-people`, `workspace-settings`, `integrations`, `report-templates` and `audit-log`) and the plain researcher grant for everything else, so the right never opens project data. `PUT /api/tenant/members/{user_id}/admin-rights` (`setMemberAdminRights`) gives or removes it and records `member.admin-rights-given` or `member.admin-rights-removed`. It locks every holder's membership row before it counts them, so two holders cannot remove each other at the same moment, and it answers 409 `last-admin` when the last holder would lose it and 409 `admin-rights-need-researcher` for a reviewer. Unlike a role change, a holder may give up their own right while another holder remains. A holder's role cannot become reviewer (409 `holds-admin-rights`), so the right always goes first through the route that guards the last holder. Invitations and the platform's `addMember` take `admin_rights` too, and a draft with a reviewer and the right is a 422. In tests, `person(..., admin_rights=True)` and `make_workspace(..., admins={"admin"})` in `tests/workspace_support.py` make a researcher with admin rights. Erasing a person through the platform still deletes their memberships when they were the last holder, because erasure must not be refused. An operator then adds a new holder through `addMember` or an invitation with the right.

## Database dependencies close before the response

`TenantConnection` and `PlatformConnection` use `Depends(..., scope="function")`, so the transaction commits or rolls back before FastAPI sends the response. With the default scope the commit runs after the response is sent, and a failed commit would follow a 200. Source: IAM-004 log entry.

## Project routes go through project_access

A route that touches a project's cases or slides reads the effective grant from `parfocal_api.project_access.project_grant`, which combines the workspace grant with the person's project role through `permissions.in_project`. Reads call `require_reading`, which answers 404 to members without read access and to anyone outside a de-identified project, and 403 `emergency-access-needed` to researchers outside a clinical project, with or without admin rights. Lists filter with `readable`. Service accounts skip project roles and keep their workspace scopes. Never check `project_members` by hand in a route ([ADR 0065](../adr/0065-project-role-enforcement.md)).

## Test helpers for workspaces and projects

CI runs `pytest -m 'not db'` in the `test` job without Postgres and `-m db` in the `db` job, so a test that calls the API or the database needs the `db` mark (`pytestmark` for the module, or `@pytest.mark.db` when the module mixes pure tests). Locally, run both selections, because `-m "db or not db"` passes a test with a missing mark. `ApiAs` sets one dependency override for the signed-in principal, so `api(person)` changes who every client acts as. Call `api(person)` right before each request and never keep a client for one person across a call made as another, or the request silently runs as the last person used. This cost time three more times on 2026-10-18 (an export test, a retention test and a consensus test), so check it first whenever a test sees the wrong person's data or a 403 it should not.

`tests/workspace_support.py` makes a workspace (`make_tenant`), people (`person`, or `make_workspace` for both), a project (`make_project`), a project role (`join_project`), a case (`make_case`) and a slide in a case or loose (`make_slide`), and `tests/case_support.py` seeds a clinical project with a patient, a case, slides and a loose slide inside a transaction. `tests/test_harness.py` uses every factory once, as the example to copy. A test that reads cases must give its principal a project role first, or it gets 404. `test_project_roles.py` computes the expected status of every project route from the matrix, so a new project route only needs an entry in `OPERATIONS`.

## The permission matrix test runs calls in a fixed order

`test_every_guarded_endpoint_follows_the_matrix_for_every_role` runs the calls in `GUARDED_CALLS` sorted by operation name for three seats, a researcher, a researcher with admin rights and a reviewer. Each seat has its own seeded workspace, whose lead owns the projects and holds the task assignments. The lead is the seat itself for the two researchers and the plain researcher for the reviewer, because two seats that may both delete, sign off or erase would otherwise find the second call already done. A call that changes state must not break a later one. Archive and restore act on `spare_project`, emergency access asks for `outside_project`, `setMemberAdminRights` gives the right to a seeded `deputy`, and `revokeInvitation` pops one seeded invitation per seat. Building `PLACEHOLDER` runs every lambda once at import, so a test that reuses it copies it with fresh lists (`dataclasses.replace`). The tenant isolation suite gives each GET route in `GET_ROUTES` the role that may call it, because no single role reads them all.

## Logging

Log with `logging.getLogger("parfocal....")` and put values in `extra` under keys from `scrubbing.ALLOWED_FIELDS`. Any other key is written as `[redacted]`. Code that reads a name, email or identifier calls `structured_logging.register_sensitive` so the rest of the request cannot leak it, as `identifiers.read_patient` does. Tests capture output with `configure_logging(..., stream=io.StringIO())` and must remove the handler afterwards, and should filter lines by logger name because the test client's `httpx2` logs each call ([ADR 0068](../adr/0068-structured-logging-on-the-standard-library.md)).

## Reviewers reach only their task slides

A project reviewer holds `see-slides` and `review` as "in their tasks". `project_access.reads_slide` and `require_slide_reading` let them read a slide only when they hold an assignment on it in a task that is not archived, and `reviews_slide` lets them draw annotations there. A case shows them only their task slides, `listCases` lists the cases that hold those slides, and `readable_slide` filters result set lists the same way ([ADR 0078](../adr/0078-review-task-model.md)). Task lists and task details filter on the reviewer's own assignments in that task, not on any task that shares a slide with them. The permission matrix test seeds the reviewer as a project viewer, so annotation writes there stay in `NEEDS_A_TASK` and get 403.

## Object IDs

`parfocal_common.object_ids` writes and parses every ID form of [ADR 0071](../adr/0071-object-id-grammar.md): `T2·C145` on screen and `T2.C145` in ASCII, `T6⁺` and `T6+`, split suffixes such as `T2a`, and the full path `P07/S26-04812/A1/T2.C145` with each segment percent-encoded and `~` for a loose slide. Parsing ignores case and spaces, keeps split suffixes lowercase, and `ObjectId.key` drops the region prefix, so `T2·C145` and `C145` compare as the same cell. Python's `quote` leaves `~` unencoded, which is why a case may not be called `~` (`CaseDraft` refuses it), while `S26~1` is fine. `by_area` numbers regions and zones largest first, and `in_reading_order` numbers cells by centroid y, then x, then input order. Every number comes from `parfocal_api.numbering.reserve`, which takes a contiguous range from `slide_counters`, so annotations and imports share one counter per slide and letter. When a new set arrives, `parfocal_ingest.matching` keeps IDs across sets: regions match one to one at IoU 0.5 or more (STRtree candidates, best IoU first), and cells when their centroids are within 4 µm (`cell_distance` turns that into pixels, 16 px without a scale, KD-tree candidates, closest first). Unmatched new objects get numbers in the ADR 0071 order through `Matching.numbers`, and unmatched old ones are listed as missing. Class is ignored, so a retyped object keeps its ID.

## The reviewed layer

A reviewer's fixes never touch the AI set ([ADR 0079](../adr/0079-reviewed-layer.md)). `review_edits` holds one row per task, slide, reviewer and AI object (`T` or `C`, no person mark or split suffix) with the new class, the new outline or a delete, and clearing the row is undo. Added objects are annotations with `task_id` set, numbered T⁺ and C⁺ from the slide's counters. `listAnnotations` leaves task annotations out, so reviewers do not see each other's additions on the slide, and only the author or a project owner changes them. Cell numbers are checked against the slide's `C` counter, because the cells themselves are in chunk files. `getReviewedLayer` compares a layer with its set. Its counts come from the result set row and the edit rows, so it never reads a chunk.

## Review states are derived, four moves are stored

`parfocal_api.review_states` follows [ADR 0069](../adr/0069-slide-pipeline.md) and [ADR 0080](../adr/0080-disagreement-rule-and-sign-off.md). `slide_state` and `reviewer_state` are pure functions of stored facts: the result set's status and source, `submitted_at` per assignment, whether the reviewer saved any work on the slide (a reviewed-layer edit or a task annotation, and verdicts once GUIDE-001 exists), open disagreements and sign-off. A slide shows its earliest reviewer state until everyone has submitted, then the task state. `check_move` decides submit, reopen a review, sign off and reopen a task for an actor and returns a refusal code, and the routes turn that into a problem. Sign-off is stored as `signed_off_at` on the task, and it locks reviewer moves and the reviewed layer until an owner reopens. Open disagreements are always 0 until ADJ-001 counts them. The permission matrix seeds one task per state (unsubmitted, submitted, ready to sign off, signed off), because its calls run in a fixed order and each move changes the state the next one needs.

## Verdicts and the retype that comes with wrong class

`parfocal_api.verdicts` keeps one verdict per task, slide, reviewer and AI object ([ADR 0072](../adr/0072-verdicts-reasons-and-opinion-forms.md)), and the database checks that only `disagree` has a reason, that the reason fits the kind, and that only `wrong_class` names a class. A `wrong_class` verdict writes the same class into the reviewer's layer in the same transaction. Changing the verdict away from that class, or clearing it, takes the retype back out, and if the layer row also holds an outline or a delete only its class is cleared. The note is classed `phi` and never goes into the audit details. Verdicts lock at sign-off like the layer, and a verdict counts as work for the `in-review` state.

## Scope and progress are pure functions

`parfocal_common.scope` decides which objects of a task slide are in scope and counts progress against them, so the API and the workers share one definition. The random cell sample is `random.Random(f"{seed}:{slide_id}")` over the sorted cell numbers, which makes it the same for every reviewer, independent of input order, different per slide and per task, and stable across runs. `CPython`'s `random.sample` has not changed its algorithm in years, and `packages/py-common/tests/fixtures/scope-slide.json` stores one sample so a change would fail the test. Cell scopes need the slide's cell numbers and scores, which live in the chunk summary ([ADR 0076](../adr/0076-annotation-and-ai-result-storage.md)), so the caller passes candidates in. Progress counts only judgements inside the scope.

## The disagreement queue is derived

`parfocal_api.disagreements.queue_of` builds the queue from stored verdicts each time ([ADR 0080](../adr/0080-disagreement-rule-and-sign-off.md)). A slide counts only when every reviewer assigned to it has submitted, and `parfocal_common.disagreements.why_queued` labels an object `reviewers-differ` when its verdicts are not all the same and `against-the-ai` when they all disagree. With the owner's rule these are the only two cases: as soon as reviewers differ the object is queued anyway, so "more than half disagree" adds the unanimous case and the single-reviewer `disagree`. A reviewer reopening a slide takes its objects out of the queue until they submit again. The open count feeds the `disagreement-queue` state and refuses sign-off. A decision on a queued object (`keep-ai` or `go-with-reviewers`, ADJ-006) takes it out of the open count but leaves it listed with the decision, and clearing the decision puts it back. Only project owners decide, only objects that are queued right now, and not after sign-off. A decision stays stored if a reopen takes the object out of the queue, and applies again if it comes back. Reviewers get 403 on the queue, and owners and viewers read it.

## The case CSV import is all or nothing

`POST /api/projects/{id}/case-imports` (`parfocal_api.case_imports`) takes a CSV with the columns `case`, `slide`, `barcode`, `stain`, `patient_name`, `mrn`, `birth_date`, `sex` and `age_years`, one row per slide, with only `case` required. Headers are matched ignoring case, spaces and dashes, and the delimiter is sniffed. A planning pass reads what already exists and collects every problem with its row and column. Nothing is written when there is any problem or when `dry_run` is true, which is the default. A re-run is idempotent: a case is found by its label, a slide by its case and label, and a patient by the blind index of the MRN, so the same file twice creates nothing the second time. Patient columns are refused in a de-identified project, a row whose patient differs from an earlier row of the same case is refused, and so is a case that already belongs to a patient with another MRN. Imported cases get the source `import` (migration `0031`) and one `case.created` audit entry each.

## Opinion answers merge into a draft

`parfocal_api.opinions` keeps one opinion per task, slide and reviewer on the form version the task pinned, so publishing a new form never changes what an answer means. A save merges the given answers into the stored ones, and `null` removes an answer, which suits autosave per question. Each answer is checked against its question's kind (a whole number inside the scale, one of the choice options, a boolean, or text within the length), and an unknown key is refused. The draft flag is not stored: an opinion is a draft while its assignment has no `submitted_at`, so submitting locks it and reopening unlocks it. Answers are `phi`, because a doctor may write identifying text, and the audit entry names only the keys. A saved opinion counts as work for the `in-review` state. ## Home is one read built from the same queries

`GET /api/me/home` (`parfocal_api.home`, [ADR 0085](../adr/0085-home-aggregate-api.md)) is open to every member and gates its own blocks. A principal without `see-slides` gets empty tasks and projects and still gets the announcements. Since IAM-024 (admin as a right of a researcher) every member role has `see-slides`, and a researcher with admin rights sees only the projects they have a role in. The task list reuses `my_work.my_review_tasks` without the submitted and signed-off tasks, ordered by due date with undated tasks last. The resume target is the newest of my verdicts, reviewed-layer edits and added objects (by `updated_at`) on a slide whose assignment has no `submitted_at`, in a task that is neither archived nor signed off. Added objects get the `+` in their ID. With none of those it falls back to the first open task's next slide, with no object, and `camera` stays null until HOME-003 stores it. Project cards count what the member may read: a reviewer's card shows only the slides of their own tasks. A slide counts as reviewed when any task holds a submitted assignment for it. `open_disagreements` is the sum of the open queue over the unsigned tasks of the projects I read whole, so it is null for a reviewer and 0 for an owner with nothing open. The queue only counts slides that every reviewer has submitted, so a test must submit before it expects anything queued.

## Rate limits are counted in `authenticate`

`parfocal_api.rate_limits.seconds_to_wait` upserts one counter per person (or service account) and one per workspace into the UNLOGGED `rate_counters` table, inside the transaction `authenticate` opens anyway ([ADR 0088](../adr/0088-rate-limits-in-postgres-and-at-the-edge.md)). Over a limit the request gets 429 `rate-limited` with `Retry-After`. The column `count` must be labelled in `RETURNING` (`hits`), because a SQLAlchemy row is a tuple and `row.count` is its method. Tests that override the principal with `ApiAs` never reach `authenticate` and are never limited. A limit test should start away from the end of a minute, because the windows are fixed minutes. `signed_in_browser(database, **changes)` takes setting changes such as a low limit.

## Personal data is found from the table models

`parfocal_api.personal_data.person_columns` lists every workspace table with a `user_id` or `*_user_id` column, and the export reads each under that workspace's scope ([ADR 0090](../adr/0090-access-export-and-erasure.md)). Invitations are matched by email, and users, sessions and the audit tables are handled by name. `test_every_personal_column_is_exported_or_has_a_reason` fails when a table holds a `personal` column and is in none of those lists, so a new table that names people needs a person column, an entry in `EXPORTED_ELSEWHERE` or a reason in `NOT_EXPORTED`. Erasing a person removes only the memberships nothing points at, using a savepoint per membership, because review assignments and emergency grants reference memberships without a cascade.

## Next and previous slide come from the list the slide was opened from

`GET /api/slides/{slide}/neighbours` (`parfocal_api.neighbours`) takes `from=task` with `task_id`, `from=all-slides` with the same filters as My work's All slides, or `from=list` with up to 200 `ids` for lists the client holds, such as search results until CASES-009 (search API) exists. A reviewer steps through their own slides in task order, and someone who reads the whole project and holds no assignment steps through every task slide. `skip_submitted` (on by default) leaves out the caller's submitted slides but keeps the current one. A sent list keeps its order and drops slides the caller cannot read. The answer carries the current slide, the neighbours, the position, the total and `at_end`. All slides is read in full through `list_my_slides`, which is fine at pilot scale like ADR 0082 says.

## Notification targets are resolved, not linked

Emails link to `/go/{notification id}`, and the app asks `GET /api/me/notifications/{id}/target` for a structured target ([ADR 0091](../adr/0091-notification-catalogue-and-targets.md)). A new `NotificationKind` needs a `CATALOGUE` entry with its target kind, subject, line and channels, a migration for the `kind` checks on `notifications` and `notification_preferences`, and a case in the resolver test. `test_every_kind_has_a_target_and_a_template_without_details` fails otherwise. The route is listed in the permission suite as `own-notification`, because only the recipient may open it and no single call works for every role.

## The inbox and mutes

`parfocal_api.inbox` serves the inbox ([ADR 0119](../adr/0119-inbox-mutes-for-projects-tasks-and-cases.md), inbox mutes). `GET /api/me/notifications` lists the caller's in-app rows newest first, filtered by repeated `kind` values, `read` and `muted`, in keyset pages that reuse My work's cursor (50 rows, at most 200). Items carry the `/go/{id}` link, the catalogue's target kind, the target id, the payload, the project, task and case and the muted flag, and the target itself is still resolved on open. `muted` defaults to false, so the main list leaves muted rows out and `muted=true` shows only them. `GET /api/me/notifications/counts` lists every kind with its total and unread count over unmuted rows, which is what the bell's badge shows, and reports `muted` and `muted_unread` apart. `POST /api/me/notifications/read` takes `ids` (at most 200) or `all` with optional `kinds` and `up_to`, marks muted rows too, and touches only the caller's unread rows, so someone else's id changes nothing and a second call keeps the first read time.

`notify()` fills `project_id`, `task_id` and `case_id` from the target through `context_of`. For a recipient who muted any of them it still stores the row, with `muted` set, `realtime` off and no email, unless the kind is in `BREAKS_MUTES`. That set comes from the `breaks_mute` field every catalogue entry must declare (mentions, task assigned, task due soon and emergency access today), so a new kind cannot skip the choice and `test_every_kind_declares_whether_it_breaks_through_a_mute` pins the set. Unmuting sends nothing old, and muted rows keep their flag. A new target kind needs a case in `context_of`, or its notifications cannot be muted. `PUT /api/me/notification-mutes/{subject}/{id}` checks that the caller reads the project, task or case (404 `mute-subject-not-found` otherwise) and marks their pending emails for it as skipped, except for kinds in `BREAKS_MUTES`. The permission suite lists it as `own-notification`, because in the seeded matrix workspace the researcher with admin rights has no role in the shared project and no single mute works for every seat. The counts route is `PUBLIC` in the isolation suite because its body holds only numbers, and `test_inbox.py` checks counts across workspaces instead.

## Emails are rendered from the reviewed template set

`parfocal_api.email_templates` holds the only email templates: the invitation and one per notification kind, built from the catalogue's subject and line ([ADR 0039](../adr/0039-email-through-resend-with-phi-rules.md)). A template takes only `recipient_name`, `workspace_name` and `link`, and `render` refuses any other value, so a case or patient field cannot reach an email. The rendered subject, text and HTML travel in `EmailMessage`, and the senders still log only the template name and link. Adding a template or a parameter fails `test_the_template_set_and_its_parameters_are_the_reviewed_ones` until the test is updated, which is the review the ADR asks for. The catalogue lives in `parfocal_api.notification_catalogue`, apart from `notifications`, because the templates and the notification service import each other otherwise.

## Email delivery takes the time as an argument

`deliver_pending_emails(connection, sender, origin, now)` decides per person from their schedule on the user row, so tests pass `now` instead of waiting ([ADR 0092](../adr/0092-email-digest-and-quiet-hours.md)). Quiet hours are compared in the person's time zone and may cross midnight. Digest windows count from the oldest waiting email's `created_at`, which the database sets, so a test adds the window to the real current time. Emergency access is never held or batched.

## Every call is also sent from another workspace

`test_no_call_from_another_workspace_changes_this_one` in `test_permissions.py` seeds two fresh workspaces, sends every guarded and member call with the first workspace's ids as each role of the second, and compares an MD5 of every row of every tenant table of the first before and after. `test_every_operation_declares_a_permission_or_why_it_is_open` already forces a new route into `GUARDED_CALLS` or `MEMBER_CALLS`, so a new route that writes across workspaces fails this test without any extra work, and a 5xx from a foreign id fails it too. Run as the first workspace's own members, the same calls change several tables, among them annotations, cases, review assignments and disagreement decisions, which is how the test was checked. Reads are covered by the isolation suite, writes by this test.

## Search reads through the same policies as every list

`GET /api/search?q=&scope=` (`parfocal_api.search`, [ADR 0094](../adr/0094-search-on-postgres.md)) matches projects, cases and slides by any part of their name or label, people by name within the workspace, and object paths from the right (`P01/S26-1/A1/T3`, `S26-1/A1/T3`, `~/loose/T1` or `A1/T3`), up to 20 hits per kind. Reads go through `readable` and `readable_slide`, so a reviewer finds only the slides of their tasks. Patients are found only by whole words through the blind tokens, in clinical projects the searcher reads whole, and come back as their cases (`patient-case`) without the name. An object hit points at the slide and the object ID, and does not check that the object exists.

## Blinding and the first read live in one module

`parfocal_api.blinding` decides what a reviewer may see ([ADR 0118](../adr/0118-blinding-and-a-kept-first-read.md)). `sees_reviewer` opens another reviewer's verdicts, layer, opinion, export, first read and added objects to a project reviewer only when both hold an assignment on that task slide, the AI is not hidden for the reader, and the task is not blinded or the reader has submitted. Project owners and viewers always pass, and admin rights add nothing. `ai_hidden` (a column filter) and `ai_hidden_on` or `require_ai_shown` (one slide) hide the AI from a project reviewer whose first read is open on that slide in any unarchived task, so a second task on the same slide cannot leak it. A new route that returns another reviewer's work or anything the AI produced must call one of them, and `test_blinding.py` holds the table of roles and phases to extend. `POST .../first-read` copies the opinion answers and the added regions and cells into `review_assignments.first_read`, and the trigger `review_assignments_first_read_kept` refuses any later change to it or to `first_read_at`, even for the owner. In a task that hides the AI, verdicts and edits answer `first-read-open` and submit answers `first-read-needed` until it is recorded. The permission matrix seeds `hidden_task` for the record call and `first_read_task` with a stored first read for the read call, because its calls run in name order.
