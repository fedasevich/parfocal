# 0129. The prototype moves into React and becomes the design source

- Date: 2026-11-01
- Status: Proposed
- Deciders: Yurii Fedas
- Backlog: adds the PROTO epic (prototype in React) with PROTO-000 (research check for the fake data layer), PROTO-001 (freeze the redesigned prototype), PROTO-002 (fake data layer for the app and the catalogue), PROTO-003 (home, My work and the shell), PROTO-004 (project page and upload), PROTO-005 (model runs and jobs), PROTO-006 (new review task), PROTO-007 (slide view, guided review and the opinion form), PROTO-008 (disagreements, sign-off and the evaluation report), PROTO-009 (admin, setup, sign-in and empty and error states), PROTO-010 (make the React app the design source) and PROTO-011 (every kit component in rough form). Edits DS-000 (design system tooling check) so it waits for the freeze, and every component task of the DS epic (design system) so it hardens the rough component instead of starting from nothing.

## Context

The design source is two Claude artifacts, the UX kit and the hi-fi mock. The mock is one HTML file of about 10,000 lines. Every design change means editing that file, which costs many tokens per change, and a component that several screens copy has to be changed in each copy. The kit and the mock can also disagree, because nothing ties a kit component to the screens that use it.

The repository has no screens yet. `apps/web` is a Vite build with typed config, and `packages/ui` and `packages/tokens` are empty scaffolds. The backend of the review loop is built, and the API client is generated by Orval from OpenAPI ([ADR 0017](0017-orval-api-client.md)). The owner is still in a redesign round of both artifacts.

Two written rules touch this. `AGENTS.md` names the two artifacts as the design source. The "How to use" section of the backlog says, from the gap review ([ADR 0023](0023-gap-review-backend-first.md), superseded by [ADR 0053](0053-ai-results-review-direction.md), which kept this rule), that UI tasks are added only when their screens settle in the prototype. The owner also asked to choose the styling approach and the component primitives library before STACK-007 (component primitives and styling) is decided (decision 15 in [decisions.md](../decisions.md)).

## Options considered

1. Keep the artifacts as the design source and build each screen when its feature UI task comes up. Nothing is ported, but every design change stays expensive, design problems are found only when a screen is finally built, and the kit and the mock keep drifting from each other.
2. Port the prototype into `apps/web` and `packages/ui` once the current redesign round is frozen. The kit becomes the component catalogue in Storybook, and the mock's screens become routes assembled from those components over fake data. The React app then becomes the design source. A change to a component is made once and shows on every screen, design problems show in a real browser at real sizes, and each feature UI task shrinks to wiring a finished screen to the API. The port has a one-time cost, trying out a design idea becomes a code change, a screen on fake data can look finished when it is not, and the port has to wait for decision 15 (styling and component primitives) and STACK-012 (frontend testing stack).
3. Build a separate throwaway prototype app, such as `apps/prototype`, free of the design system's test rules. It is the fastest way to get clickable React screens, but every screen is built twice and the prototype drifts from the product the same way the artifacts do.
4. Port now, during the redesign round. The React baseline exists sooner, but every screen the redesign changes is ported twice.

## Decision

Option 2, because it is the only one where a design change is made in one place and that place is the product itself.

- The port starts only after the owner says the current redesign round is done. PROTO-001 (freeze the redesigned prototype) records each artifact's version, keeps a frozen copy and lists every screen, scene and kit page in an inventory that maps each one to the task that owns it and the API it reads.
- Speed comes first. PROTO-011 (every kit component in rough form) builds every kit component from the frozen kit with a Storybook story per state, and the PROTO screen tasks build every mock screen from those components, so the owner can click through the whole design and change it before the production work locks it in. Rough means the right names, props, layout, tokens and clicks, with only smoke tests. The tasks of the DS epic (design system) and the SHELL epic (application shell) then harden the same components with their visual, accessibility and interaction tests, so nothing is built twice and there is no second catalogue.
- Screens run on fake data served by MSW in the dev server and in Storybook. Operations the API already has get handlers generated by Orval from `openapi.json`, so their fake data has the real types. Screens with no API yet use hand-written fixtures. One scenario seed holds the mock's people, projects, slides and object IDs so that every screen tells the same story. A badge marks every screen that still shows fake data, and builds for staging and production contain no handlers.
- Each feature UI task, such as HOME-002 (launchpad home) or GUIDE-002 (guided review), starts from its ported screen, wires it to the API, adds the behaviour and its tests and removes the screen's fake data.
- The slide canvas is a placeholder until the viewer tasks put Viv there.
- When every screen is ported, PROTO-010 (make the React app the design source) applies the edits listed below. The artifacts are then kept as frozen history. A large new idea can still be sketched in a throwaway artifact first, and it is ported into the app once it is chosen.

## Consequences

- The backlog gains the PROTO epic. PROTO-001 (freeze the redesigned prototype) is on hold until the owner says the redesign round is done, and every later PROTO task depends on it.
- DS-000 (design system tooling check) now depends on STACK-007 (component primitives and styling) and PROTO-001 (freeze the redesigned prototype), PROTO-011 (every kit component in rough form) depends on DS-000, and every component task of the DS epic (design system) depends on PROTO-011, so no component is built before the owner has picked the styling and the redesign is frozen, and each production component starts from its rough copy.
- The "How to use" section of the backlog gains a rule that UI tasks wait for the freeze and decision 15 (styling and component primitives), and that a feature UI task starts from its ported screen.
- Until this record is accepted, the live rule still says UI tasks wait for settled screens. The PROTO epic is consistent with it, because every task except PROTO-000 (research check for the fake data layer) waits behind the freeze.
- PROTO-010 (make the React app the design source) changes these lines once every screen is ported: the design source sentence in `AGENTS.md`, the two artifact bullets at the top of `docs/BACKLOG.md`, the "Design sources" section of `docs/project/overview.md` and the "How to use" rule that UI tasks wait for screens to settle in the prototype. They stay as they are until then.
- Where the frozen copies live and whether the owner reviews each screen group before it is ticked are decisions 16b and 16c in [decisions.md](../decisions.md).
