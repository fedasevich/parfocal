# 0049. Server state in TanStack Query v5 on the generated client, with event-driven invalidation

- Date: 2026-10-15
- Status: Accepted
- Deciders: Yurii Fedas (owner standing approval)
- Backlog: STACK-004 (server state and data fetching), touches STACK-008 (API contract and client generation), STACK-024 (realtime transport), STACK-003 (routing), STACK-005 (client UI state), STACK-006 (viewer hot-path state outside React), ANN-020 (annotation persistence API), COLLAB-002 (threads API)

## Context

The web app is a React 19.3 SPA with React Compiler on ([ADR 0016](0016-react-19-spa-compiler-strictmode.md)) and compiles with TypeScript 7 under strict flags, including `exactOptionalPropertyTypes` ([ADR 0006](0006-monorepo-tooling.md)). The API client is generated by Orval from FastAPI's OpenAPI 3.1 with `client: "react-query"` ([ADR 0017](0017-orval-api-client.md)), and `@tanstack/react-query` 5.104.1 is already a dependency of `packages/api-client`. Realtime events come from Durable Objects and carry only ephemeral signals. Postgres stays the system of record, and "clients refetch on reconnect" ([ADR 0003](0003-pilot-platform-architecture.md)).

Four needs shape the choice.

- Cases, worklists, threads and annotation lists are server state that many screens read. They need caching, deduplication and invalidation.
- Realtime events (STACK-024) must make that state fresh without the event carrying data.
- Annotation edits must feel instant. A pathologist drawing and adjusting shapes cannot wait for a round trip, and a failed save must not leave the screen lying.
- Screens should read as "data is there" code. Loading and error branches belong at boundaries.

Two limits keep the scope small. Viewer hot state (camera, pointer, tool state) lives outside React ([STACK-006 (viewer hot-path state outside React)](../BACKLOG.md)), and the editable annotation document is its own client model (ANN-001, annotation document model). Query handles how those documents are loaded and saved, not what happens on each pointer move. Model output chunks (typed arrays per job tile, STACK-021) are not server state in this sense and never enter the Query cache.

Versions were checked on 2026-10-15. The spike numbers are in [results/2026-10-15-server-state-spike.md](../results/2026-10-15-server-state-spike.md).

## Options considered

1. TanStack Query 5.104.1. Orval generates its hooks, keys and options already, so no new generator is needed. It has `useSuspenseQuery`, `useSuspenseQueries`, `QueryErrorResetBoundary`, `onMutate` with `cancelQueries`, `setQueryData` and rollback, a mutation retry policy, `isMutating` and key-based invalidation. In the spike all of those worked with TypeScript 7 and the repository flags. It costs 11.2 KB gzip for the data-layer exports measured, which is more than SWR. The generated response types and the default error type need two small fixes, listed under Consequences.
2. SWR 2.5.1. It is the smallest at 6.5 KB gzip. Orval has an SWR generator (`@orval/swr` is part of Orval 8.40), and SWR has `mutate` with optimistic data and rollback options and a `suspense` option, according to its documentation (not run in the spike). Its cache is keyed by one string or array, with no cancel-and-snapshot step of the kind used for optimistic edits and no mutation state machine with retry and pause that matches TanStack's. We would write more of the annotation edit logic ourselves, and the repository already generates for TanStack.
3. RTK Query (Redux Toolkit 2.13.0). It has tag-based invalidation, which maps well onto events, and `updateQueryData` with `undo` for optimistic updates. It needs a Redux store and provider, so it costs 25.4 KB gzip in the measured entry, and the app would carry Redux for server state only. Orval 8.40 ships no RTK Query generator (no such package was found in its dependencies), so the client would be hand-written or generated by a second tool, which reopens ADR 0017. It has no Suspense hook, according to its documentation (not re-checked in the spike).
4. Plain `fetch` in effects with a small hand-written cache. Smallest, but caching, deduplication, cancellation, retry, invalidation and suspense would all be ours, for every screen.

## Decision

TanStack Query v5 is the server-state layer. The generated Orval hooks, `queryFn` and key builders are the only way screens reach the API. Details follow.

Client and cache

- One `QueryClient` per signed-in session, created at the app root. The defaults are `staleTime` 30 s, `gcTime` 5 min, `refetchOnWindowFocus` on, and retry only for `ApiError` of kind `network` or `server`, at most 3 times, with delays of 250 ms doubling to a 4 s cap. These numbers are a starting assumption and were not tuned (the tests used a 1 ms delay).
- No query persister. Nothing from the cache is written to `localStorage`, IndexedDB or any storage, because cached cases and annotations are PHI-bearing. The cache is cleared with `queryClient.clear()` on sign-out, on idle lock ([ADR 0031](0031-idle-lock-from-explicit-activity.md)), on workspace switch ([ADR 0024](0024-workspaces-are-tenants.md)) and when an emergency access grant ends ([ADR 0047](0047-emergency-access-with-a-reason.md)). Keys do not carry the tenant, so the clear is what separates tenants.
- Query data stays the generated envelope (`{ data, status, headers }`). Domain code reads it through `select: unwrap`, which checks `status === 200` and returns the typed body. Writes to the cache with `setQueryData` must patch the envelope.
- Query keys come only from the generated builders (`getGetCaseQueryKey`, `getListCasesQueryKey`). They are URL strings, so there is no prefix hierarchy between a list and a detail key. Code that needs a group uses a predicate or names each builder, never a hand-written prefix.
- Presence, cursors and other ephemeral realtime state are not server state. They stay out of Query and belong to the UI state store (STACK-005).

Invalidation from realtime events (STACK-024)

- An event carries a type and ids, never data and never PHI. It does not write into the cache. It only invalidates, and the refetch is the single source of truth.
- One module in `apps/web` maps each event type to generated keys, and a test covers each mapping. The spike's mapping is the starting point.

| Event | Invalidates |
|---|---|
| `case.updated` with a case id | `getGetCaseQueryKey(caseId)` |
| `case.list.changed` | list queries, by a predicate on the first key element `/api/cases` |
| `thread.updated` with a case id | the threads list for that case |
| `annotation.changed` with case and slide ids | the annotation list for that slide, unless a local edit is in flight |

- Active queries refetch at once. Inactive queries are marked stale and refetch on next mount, which the spike showed with no extra request.
- On a reconnect the client invalidates every active query, because events during the gap are lost and a lost message only costs a refetch ([ADR 0003](0003-pilot-platform-architecture.md)).
- Events that arrive while the local user has an annotation edit in flight for that list are ignored. The edit's own settle step refetches, so the screen does not flicker back to server state mid-edit.
- Event bursts are not measured. TODO: decide on coalescing after the STACK-024 spike.

Optimistic annotation edits with retry

- The edit mutation has a shared key. `onMutate` cancels in-flight fetches of the list, snapshots it, and patches the one annotation in the cached envelope. `onError` restores the snapshot only when no other edit is in flight. `onSettled` invalidates the list only when the last edit finishes.
- Retry covers network failures and 5xx up to 3 times, with the optimistic value kept on screen during retries. A 4xx never retries and rolls back at once. A 409 (version conflict) rolls back and the refetch shows the server's version. A 422 is a validation failure and rolls back. The tests used 422 and 500, so the 409 path is a design choice that follows the same code.
- The write is an idempotent `PUT` per annotation with the version in `If-Match`. ANN-020 (annotation persistence API) is versioned already, and this ADR adds the client edit id as a requirement for it (see Consequences).
- Dragging does not call the server per pointer move. The annotation document model owns the shape while it moves, and one mutation fires when the gesture ends.
- The mutation network mode is `online`, so edits made while offline pause and resume when the connection returns. The spike did not run this. TODO: test it.
- Edits are not persisted across a page reload, because there is no persister. TODO: ANN tasks decide whether an unsaved draft needs its own durable store.

Suspense

- Screens read data with `useSuspenseQuery` or, where the Orval option is on, the generated `use...Suspense` hooks. Suspense boundaries sit at route and panel level, with an error boundary around each and `QueryErrorResetBoundary` for the retry button. Components then have no loading branch. The spike showed `ApiError` arriving at the boundary with its kind, and a reset recovering once the case existed.
- A screen that needs more than one query uses `useSuspenseQueries` or a route loader that calls `ensureQueryData`. Two `useSuspenseQuery` calls in one component start their fetches one after the other (60.6 ms apart with a 60 ms server delay, against 0.03 ms for `useSuspenseQueries`). The route loader works with whichever router STACK-003 picks.
- No Suspense boundary wraps the viewer host, and tiles do not go through Query. The viewer host manages its own engine lifecycle ([ADR 0016](0016-react-19-spa-compiler-strictmode.md)). TODO: confirm with the viewer host that a sibling boundary re-suspending does not disturb it. The rule is a precaution until then.
- Mutations and optimistic updates use plain hooks, not Suspense.

Why TanStack Query won: the repository already generates it, it covers all four required behaviours as library features rather than code we maintain, and the size difference to SWR (4.7 KB gzip) is small against the work it saves. No budget exists to weigh it against (TODO).

## Consequences

- STACK-008 (API contract and client generation) gets three follow-ups to the Orval setup. First, set `override.query.useSuspenseQuery: true` so every GET operation also gets a Suspense hook that shares the plain key (19 hooks in the spike). Second, export `type ErrorType<Error> = ApiError` from `packages/api-client/src/fetcher.ts` so hooks type their error as `ApiError`, the class the fetcher throws. Third, add a `Register` augmentation with `defaultError: ApiError` in `apps/web`. These are not made yet and need a task beside FOUND-008 (API client pipeline). ADR 0017 stays accepted.
- App code wraps the long generated signatures in small domain hooks, as ADR 0017 already advised, and narrows the response union with `unwrap`. Under `exactOptionalPropertyTypes` the generated `get...QueryOptions` objects do not pass to `ensureQueryData` or `useSuspenseQueries`, so those places use `queryOptions({ queryKey, queryFn })` built from the generated function and key. The spike's `caseQuery` shows the shape.
- ANN-020 (annotation persistence API) must accept `If-Match` on an annotation `PUT`, return 409 on a stale version and make a repeat of the same edit safe, for example through a client-generated edit id, so a retry after a lost response does not turn a saved edit into a conflict. This case was not run. TODO: add the edit id to ANN-020.
- STACK-024 (realtime transport) must keep events as ids and types only, and its spike must measure event to refetch latency on staging, which this spike did not (TODO). Its "clients refetch on reconnect" line is now a concrete rule.
- STACK-005 (client UI state) takes presence and other ephemeral state. This ADR fixes the first line of its split: server state is in Query.
- Cache clearing on session events is a requirement for IAM work (idle lock, workspace switcher) and has no code yet.
- Supersede this record if bundle budgets or a measured cost make SWR worth the extra hand-written edit logic, or if Orval gains an RTK Query generator and the app takes on Redux for other reasons.
