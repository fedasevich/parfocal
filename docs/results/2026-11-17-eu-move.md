# Result: an EU web container reaches the Frankfurt database in 14 to 16 ms and answers the Mac in 0.16 s through Dublin, while today's signed-in calls take 1.5 s and 4.1 s

- Date: 2026-11-17
- Backlog: OPS-031 (move the API and database to the EU), a slice of OPS-020 (pin storage, database and Modal functions per region). Follows decision 140 (moving production's API and database to Europe) in [decisions.md](../decisions.md), option A without the warm container
- Kind: measurement from the owner's Mac in Europe with curl, and a probe app in Modal environment `dev`
- Commit: the OPS-031 branch, before the cutover
- Environment: production `app.parfocal.eu` at v0.5.1 for the before numbers. Modal `dev` for the probe
- Data: the seeded showcase. The signed-in calls used a session row minted for the seeded user `seed:ada@showcase.invalid` by a scratch Modal run in `main` with the app's own session key, valid 6 hours

## Question

How fast are warm signed-in calls today, and how much do the EU pin and the Dublin entry change them?

## Method

- Before: `curl` from the Mac, one warm-up call and then ten calls in a row to each route, recording `time_starttransfer` and the `Server-Timing` header, at 13:10 UTC.
- Probe: a scratch app `parfocal-region-probe` in Modal `dev` with three ASGI functions, `routed` (`region="eu"`, `routing_region="eu-west"`), `guarded` (the same with `requires_proxy_auth`) and `plain` (`region="eu"` only). Each container timed five TCP connects to the Frankfurt and the Virginia Neon poolers, spawned an unrouted helper, and was called six times from the Mac. The app was stopped after the run.

## Before, production with the API unpinned and Neon in Virginia

Almost all of the handler time is database time (`db` equals `app` within 3 ms on every route), so the round trip to Virginia dominates.

## Probe in Modal dev

| | `routed` (eu, Dublin entry) | `plain` (eu, Virginia entry) |
|---|---|---|
| `MODAL_REGION` | `eu-south` | `eu-west` |
| TCP connect to the Frankfurt pooler, five tries | 29.7, 16.2, 14.5, 13.7, 16.1 ms | 27.5, 15.9, 13.7, 14.5, 14.8 ms |
| TCP connect to the Virginia pooler, five tries | 114.8, 98.4, 99.2, 100.1, 101.4 ms | 119.3, 83.8, 83.6, 84.8, 85.1 ms |
| First byte from the Mac, six calls | 0.163, 0.213, 0.157, 0.514, 0.163, 0.153 s | 0.443, 0.495, 0.461, 0.464, 0.460, 0.464 s |
| Web address | `<workspace>--<app>-<function>.eu-west.modal.run` | `<workspace>--<app>-<function>.us-east.modal.run` |

- A routed function spawned an unrouted one with `.spawn()` and got its answer, so the web function's own spawns of `events`, `ingest` and the GPU pools keep working. Only calls into a routed function must avoid `.spawn()`, and nothing calls the web function except HTTP.
- `requires_proxy_auth`, `modal.concurrent` and `enable_memory_snapshot` deploy together with `routing_region`, and the guarded function answered 401 without a token.
- The routed address carries the routing region, so the new function has a new URL. `deploy.py` reads it from the function at deploy time, so `API_ORIGIN` follows without an edit.

## What this means

- The proxy figure of 11 to 28 ms a round trip in [server region options](2026-11-17-server-region-options.md) holds: 14 to 16 ms measured once connections are warm. Virginia costs 84 to 101 ms from the same containers.
- The Dublin entry takes about 0.3 s off every call from Europe before the database is touched.
- At 9 queries `/api/me` should drop from about 1.1 s of database time to roughly 0.15 to 0.25 s, and home at 39 queries from 3.4 s to roughly 0.6 to 0.9 s. These are estimates from the per-query cost, not measured.
