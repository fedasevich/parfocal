# Result: latency proxy accuracy at 0, 50, 100 and 200 ms RTT

- Date: 2026-10-23
- Backlog: TILES-006 (latency proxy test harness)
- Kind: baseline
- Commit: 84b603f plus the uncommitted TILES-006 changes in `packages/latency-proxy`
- Environment: Apple M4, macOS 15.8.1, Node 26.9.0, Google Chrome 155.0.8059.85 headless through Playwright 1.64.0. Proxy and origin on 127.0.0.1. Other agents were running on the machine.
- Data: generated byte responses from the test origin, no slides

## Question

Does the proxy add the RTT it is set to, within the `max(10 ms, 10%)` tolerance the tests use, and does the bandwidth limit hold? The POC's `scripts/latency-proxy.mjs` was not measured, so there is no POC number to compare.

## Method

1. `pnpm --filter @parfocal/latency-proxy measure` starts the origin and the proxy, then for each RTT sends one warm-up request each way and 20 sequential 1 KiB requests alternating direct and proxied, through Node's `fetch` with keep-alive. "Added" is each proxied time minus the direct median.
2. The same script downloads 1 MB through the proxy at 0 ms RTT with three bandwidth limits.
3. `pnpm test:browser` runs `perf/request-latency.spec.ts` in Chrome once per RTT project. It times 8 sequential 64 KiB `fetch` calls and 12 parallel ones from inside the page, which was itself loaded through the proxy.

## Results

Node client, 1 KiB responses, 20 samples per row:

| Set RTT (ms) | Direct median (ms) | Proxied median (ms) | Added median (ms) | Added min (ms) | Added max (ms) |
|---|---|---|---|---|---|
| 0 | 0.20 | 0.38 | 0.17 | 0.06 | 0.75 |
| 50 | 0.43 | 52.03 | 51.60 | 50.48 | 54.46 |
| 100 | 0.38 | 102.01 | 101.63 | 100.76 | 102.98 |
| 200 | 0.58 | 202.29 | 201.71 | 200.30 | 203.13 |

Bandwidth, 0 ms RTT, one 1 MB response:

| Limit (B/s) | Expected (ms) | Measured (ms) |
|---|---|---|
| 1,000,000 | 1000 | 1002.4 |
| 5,000,000 | 200 | 201.7 |
| 20,000,000 | 50 | 52.1 |

Chrome, 64 KiB responses, from one `pnpm --filter @parfocal/latency-proxy test:browser` run. The parallel column is the fastest of three rounds of 12 requests:

| Set RTT (ms) | 8 sequential, median (ms) | min (ms) | max (ms) | 12 parallel (ms) |
|---|---|---|---|---|
| 0 | 1.10 | 0.60 | 4.40 | 3.80 |
| 50 | 53.10 | 52.50 | 54.90 | 107.10 |
| 100 | 103.50 | 102.60 | 103.70 | 207.40 |
| 200 | 202.35 | 201.30 | 202.50 | 406.90 |

A first version paced bandwidth from "now" after every 16 KiB slice. It measured 1037.3 ms, 216.4 ms and 70.2 ms for the three limits above, because timer lateness added up slice by slice. The pacing now keeps its schedule while any response is streaming and starts afresh when none is or after 5 ms of idle time.

While `pnpm test` ran every package at once, the Node tests first failed at 50 ms RTT with a median of 64.18 ms added and a throttled request at 231.7 ms against 200 ms expected, because the Python test processes loaded the CPU. Run alone they passed. The tests now check the fastest of several samples: the fastest proxied request must take at least the RTT, and it must be within the tolerance of the fastest direct request plus the RTT. Three forced runs of `pnpm turbo run test --force` then passed.

## Interpretation

- Medians are not usable as pass criteria on a shared CPU, since load only ever adds time. The fastest sample is, because no load makes a request faster than the proxy allows.
- The proxy adds the set RTT plus 1 to 2 ms, which is Node timer lateness and the extra hop. That is inside the 10 ms floor of the tolerance at every RTT.
- Twelve parallel requests take two RTTs, not one, because Chrome opens six HTTP/1.1 connections per origin. Production runs on HTTP/2 or HTTP/3, so a perf budget that depends on many requests in flight will look worse through this proxy than in the field.
- Assumption: hosted Linux runners have similar timer lateness. The tolerance has headroom, but the CI numbers are not measured yet.
